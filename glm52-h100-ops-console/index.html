read first — field-corrected reality check (2026-08)

Two hard constraints decide everything on this node, and both were verified against the live vLLM bug tracker:

1 — NVFP4 on H100 is not just slow, it is flaky right now. H100 (Hopper, sm90) has no FP4 tensor cores, so vLLM routes NVFP4 checkpoints to a Marlin weight-only fallback that dequantizes to BF16 on the fly — you lose the speed benefit, and the kernel path itself is broken: issue #34694 shows BF16 NVFP4 Marlin producing garbled output on all non-FP4 GPUs (bad exponent widening in the dequant kernel), and issue #49070 shows NVFP4-MoE on Hopper returning garbage and crashing with CUDA illegal memory access under concurrency. GLM-5.2 is a MoE model — it hits exactly this path. Fix PRs (#34577, #48929, #48624) exist but are not all merged. Do not deploy the NVFP4 checkpoint on H100 until your vLLM build carries every fix — links in module [03].

2 — FP8 does not fit. GLM-5.2 is ~744B params → FP8 weights alone are ~740–750 GB. 8×H100 80 GB gives you 640 GB, and even 8×H100 NVL (94 GB) only reaches ~752 GB — zero headroom for KV cache or context. The native-FP8 checkpoint officially needs 8×H200 (1.1 TB).

The way through: INT4 / W4A16 weight-only. 4-bit weights (~388 GB) with BF16 activations — compute runs natively on Hopper tensor cores, no FP4 kernel dependency, no dequant correctness bugs, and ~250 GB left over for an FP8 KV cache. Benchmarks show parity with the FP8 release. This is the only single-node GLM-5.2 config that is both fitting and correct on 8×H100 today.

Recommended stack

Most optimal for 8×H100: GLM-5.2-W4A16 (INT4 weights, BF16 compute) served by vLLM ≥ 0.23, tensor-parallel across all 8 GPUs, FP8 KV cache, expert parallel on. No exotic kernels — this rides the standard compressed-tensors Marlin W4A16 path that is stable on Hopper. Exact serve command:

> vllm serve — 8×H100 production flags
vllm serve lowbitcoffee/GLM-5.2-W4A16 \
    --tensor-parallel-size 8 \
    --enable-expert-parallel \
    --kv-cache-dtype fp8 \
    --max-model-len 131072 \
    --gpu-memory-utilization 0.92 \
    --tool-call-parser glm47 \
    --reasoning-parser glm45 \
    --enable-auto-tool-choice \
    --served-model-name glm-5.2 \
    --port 8000

Notes: keep --max-model-len 131072 as the production cap — pushing toward the full 1M context starves the KV cache and tanks concurrent throughput on 640 GB. Add MTP speculative decoding via --speculative-config '{"num_speculative_tokens": 3, "method": "deepseek_mtp"}' once on a vLLM build that includes it (GLM-5.2 extends MTP to 5 draft tokens on latest main). If a flag is rejected, your runtime image is older than v0.23 — pull the newest quay.io/modh/vllm CUDA tag or the upstream vllm/vllm-openai image from module [03].

Deploy configs — copy & apply

servingruntime.yaml
apiVersion: serving.kserve.io/v1alpha1
kind: ServingRuntime
metadata:
  name: vllm-cuda-glm52
spec:
  supportedModelFormats:
    - name: vllm
      autoSelect: true
  multiModel: false
  containers:
    - name: kserve-container
      # newest cuda tag incl. PR #41276
      image: quay.io/modh/vllm:rhoai-2.20-cuda
      command: [python, -m,
        vllm.entrypoints.openai.api_server]
      args:
        - --model=/mnt/models
        - --tensor-parallel-size=8
        - --enable-expert-parallel
        - --kv-cache-dtype=fp8
        - --max-model-len=131072
        - --gpu-memory-utilization=0.92
        - --tool-call-parser=glm47
        - --reasoning-parser=glm45
        - --enable-auto-tool-choice
      resources:
        requests:
          nvidia.com/gpu: 8
        limits:
          nvidia.com/gpu: 8

Decision tree at 8×80 GB

If you're capped at 8×80 GB, these are the three realistic paths — ranked by how clean they are:

[a] INT4 / W4A16 weight-onlybest tradeoff ~388 GB, real KV headroom, correct kernels. Benchmark parity with FP8. This is the recommended path in module [01] — no hardware change, no quality cliff. single node
[b] CPU / disk offload of MoE experts FP8 or BF16 weights with --cpu-offload-gb (or llm.serve-style expert offload). It fits, but tokens/sec drops hard — only acceptable for batch/offline work. fits · slow
[c] More nodes (multi-node TP/PP) Cleanest — zero quality tradeoff. 2× 8×H100 (1.28 TB) runs FP8 across nodes via Ray; RHOAI supports multi-node serving with the vLLM multinode runtime. Use if you can burst past one node. best quality
> the two questions that pick the path
# 1. Card variant: 80 GB H100 SXM/PCIe or 94 GB H100 NVL?
#    → NVL gets you 752 GB — still not enough for FP8 + KV. W4A16 either way.
# 2. Is 8 GPUs a hard ceiling, or can you burst to a second node?
#    → Can burst:  go multi-node FP8 (path c)
#    → Hard cap:   go W4A16 (path a); offload (path b) only for offline jobs
